# CertSentry

Лёгкая система инвентаризации TLS-сертификатов и раннего обнаружения инфраструктурных рисков. Это реализация **темы 2 — Certificate Radar** из технического задания Hackathon.

Проект сканирует DNS-имена, IP-адреса, CIDR и HTTPS URL, получает сертификат сервиса, проверяет срок действия, доверие к цепочке, соответствие имени и криптографические параметры. Dashboard показывает состояние сервисов, риск и рекомендации, поддерживает поиск, фильтры, сортировку и CSV-экспорт. **Certificate ChangeGuard** сравнивает сертификат с предыдущим сканированием, показывает изменения и ждёт подтверждения администратора. Инвентарь сохраняется между перезапусками в SQLite.

## 1. Требования

- Windows, Linux или macOS.
- Python 3.10 или новее.
- Node.js 20.9 или новее и npm.
- Доступ к сетевым адресам, которые нужно проверить.

SQLite входит в стандартную библиотеку Python. Отдельный сервер базы данных, Docker и дополнительные frontend-библиотеки не нужны.

Откройте <http://localhost:3000>. Backend API и его Swagger-документация доступны на <http://localhost:8000/docs>, а проверка готовности — <http://localhost:8000/health>.

## 4. Работа с Dashboard

1. Укажите цели сканирования — по одной на строку. Также принимаются адреса, разделённые запятыми или точками с запятой.
2. При желании задайте владельца и критичность сервиса. Критичность влияет на итоговый Risk Score.
3. Нажмите **Сканировать**. Успешные результаты появятся в таблице, а неудачные подключения будут перечислены с причиной.
4. Используйте поиск по сервису, CN, владельцу, Issuer или статусу. Выберите статус и нажмите заголовок колонки, чтобы сортировать.
5. Откройте строку, чтобы увидеть CN, SHA-256 thumbprint, SAN, состояние проверки цепочки и имени, факторы риска и рекомендации.
6. Нажмите **Скачать CSV**, чтобы выгрузить текущий инвентарь для отчётности.

### Certificate ChangeGuard — контроль изменений сертификата

При первом успешном сканировании CertSentry запоминает сертификат как исходную версию сервиса. При каждом следующем сканировании он сравнивает актуальный сертификат с последним состоянием и ищет изменения в thumbprint, CN, Issuer, SAN, сроках действия, доверии к цепочке, соответствии имени и криптографических параметрах.

Если сертификат или проверяемые свойства изменились, запись помечается **«Проверить»**. В раскрытии строки показываются старые и новые значения, предыдущий и текущий thumbprint, прежний и новый риск и время обнаружения. Такое изменение **не объявляется атакой автоматически**: плановая замена сертификата тоже меняет отпечаток. Администратор проверяет причину и нажимает **«Отметить изменение проверенным»**. До этого событие остаётся в списке изменений и учитывается в счётчике Dashboard. При настроенном Telegram CertSentry отправляет отдельное уведомление о новом изменении.

Повторные сканы неизменённого сертификата не создают новых событий. Изменение хранится в SQLite и остаётся видимым после перезапуска приложения. Эта функция делает CertSentry монитором изменений сертификатов, а не только сканером срока действия.

**Сценарий демонстрации:** просканируйте тестовый сервис, чтобы зафиксировать базовую версию; замените сертификат на тестовом HTTPS-сервере; запустите сканирование снова. Dashboard покажет новый thumbprint и конкретные изменившиеся поля. Подтвердите изменение и покажите, что карточка сохраняет отметку о проверке.

### Форматы целей

```text
example.com
example.com:8443
192.0.2.15
192.0.2.0/28
https://portal.example.com/login
https://[2001:db8::10]:8443/
```

Для URL используется имя узла и порт; путь запроса игнорируется. `http://` не принимается: сканер проверяет TLS. CIDR разворачивается в адреса хостов. За один запуск допускается не более 1024 уникальных адресов, чтобы случайно не создать чрезмерную нагрузку.

## 5. Как рассчитываются статусы и риск

Сроки и статусы соответствуют таблице в ТЗ:

| Срок действия | Базовый статус |
|---|---|
| Более 60 дней | OK |
| 31–60 дней | Information |
| 15–30 дней | Warning |
| 0–14 дней | Critical |
| Истёк | Expired |

Risk Score складывается из срока действия, ошибки доверия к цепочке, несовпадения имени, self-signed сертификата, слабой криптографии и отсутствия владельца. Затем учитывается множитель критичности сервиса, а результат ограничивается диапазоном 0–100. В интерфейсе каждый найденный фактор сопровождается рекомендацией. Ошибочная цепочка и несовпадение имени проверяются независимо.

Начисление баллов до множителя:

| Фактор | Баллы |
|---|---:|
| Срок действия: более 60 / 31–60 / 15–30 / 0–14 / истёк | 0 / 15 / 40 / 80 / 100 |
| Ошибка доверия к цепочке | 30 |
| Несовпадение имени | 25 |
| Слабая криптография | 25 |
| Self-signed | 20 |
| Не назначен владелец | 10 |

Множители критичности: `LOW` ×1.0, `MEDIUM` ×1.1, `HIGH` ×1.3, `CRITICAL` ×1.5. Итог усекается до целого числа и ограничивается 100. Статус по умолчанию следует сроковым окнам из ТЗ; дополнительные проблемы могут поднять статус и риск.

Проверка цепочки использует хранилище доверенных CA операционной системы. Если TLS-проверка не проходит, сканер повторно запрашивает leaf-сертификат без проверки, чтобы показать его атрибуты и зафиксировать проблему цепочки. Это не загружает и не проверяет всю PKI-инфраструктуру.

## 6. Оповещения Telegram

Без переменных Telegram бот не используется, остальные функции работают. Для включения задайте переменные **в том же терминале, где запускается backend**.

`backend/.env.example` — это список поддерживаемых переменных и их значений по умолчанию. Backend не загружает `.env` автоматически: задайте нужные переменные в окружении терминала перед запуском. Не добавляйте в репозиторий рабочие токены и приватные ключи.

PowerShell:

```powershell
$env:TELEGRAM_BOT_TOKEN = "токен-бота"
$env:TELEGRAM_CHAT_ID = "id-чата"
$env:NOTIFY_THRESHOLDS = "60,30,14,7,1"
```

Linux или macOS:

```bash
export TELEGRAM_BOT_TOKEN="токен-бота"
export TELEGRAM_CHAT_ID="id-чата"
export NOTIFY_THRESHOLDS="60,30,14,7,1"
```

Затем перезапустите backend. Уведомление отправляется при первом достижении ближайшего порога или при пересечении порога между сканированиями; повтор одного и того же оповещения подавляется. Ошибка цепочки и критичный/истёкший статус тоже вызывают оповещение. Данные бота не записываются в базу.

## 7. Настройки backend

Настройки задаются переменными окружения до запуска backend:

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `SCAN_TIMEOUT` | `10` | Таймаут одного TLS-подключения в секундах, минимум 1 |
| `SCAN_CONCURRENCY` | `50` | Параллельные подключения, от 1 до 256 |
| `NOTIFY_THRESHOLDS` | `60,30,14,7,1` | Пороги Telegram в днях |
| `THRESHOLD_OK` | `60` | Нижняя граница статуса OK |
| `THRESHOLD_INFO` | `30` | Верхняя граница Information |
| `THRESHOLD_WARNING` | `14` | Верхняя граница Warning |
| `RADAR_DATABASE_PATH` | `backend/data/certificates.sqlite3` | Путь к SQLite-файлу |
| `TELEGRAM_BOT_TOKEN` | не задан | Токен Telegram-бота |
| `TELEGRAM_CHAT_ID` | не задан | Чат для уведомлений |
| `FRONTEND_ORIGINS` | `http://localhost:3000` | Разрешённые браузерные origins через запятую |

Пороговые переменные задавайте согласованно: `THRESHOLD_OK` выше `THRESHOLD_INFO`, `THRESHOLD_INFO` выше `THRESHOLD_WARNING`, а `THRESHOLD_WARNING` неотрицателен. При некорректном порядке backend сообщит об этом при запуске.

## 8. API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка backend |
| `POST` | `/api/v1/scan/run` | Запуск сканирования |
| `GET` | `/api/v1/certificates` | Страница инвентаря с фильтром, поиском и сортировкой |
| `POST` | `/api/v1/certificates/{id}/acknowledge-change` | Подтверждение проверки найденного изменения сертификата |
| `GET` | `/api/v1/metrics/summary` | Счётчики и распределение статусов |
| `GET` | `/api/v1/reports/export` | CSV-отчёт |

Пример запроса на сканирование:

```json
{
  "targets": ["example.com", "https://portal.example.com:8443"],
  "criticality": "HIGH",
  "owner": "Platform Team"
}
```

Допустимые значения `criticality`: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`. Ответ сканирования содержит успешные сертификаты и отдельный список ошибок подключения.

Пример чтения инвентаря с фильтром, поиском и сортировкой:

```text
GET /api/v1/certificates?page=1&page_size=25&status=CRITICAL&query=portal&sort_by=days_left&sort_order=asc
```

Параметры списка: `page` (начиная с 1), `page_size` (1–100), `status`, `query`, `changed_only=true` (только неподтверждённые изменения), `sort_by` (`hostname`, `owner`, `issuer`, `valid_to`, `days_left`, `status`, `risk_score`, `criticality`, `change_pending`, `change_count`) и `sort_order` (`asc` / `desc`).

## 10. Данные и обслуживание

- Файл `backend/data/certificates.sqlite3` создаётся при первом запуске backend.
- Повторное сканирование того же hostname и порта обновляет существующую запись и сохраняет её ID. ChangeGuard сохраняет базовый thumbprint, счётчик изменений и последнее сравнение, включая подтверждение администратора.
- Чтобы очистить демонстрационный инвентарь, остановите backend и удалите SQLite-файл и файлы `certificates.sqlite3-wal` / `certificates.sqlite3-shm`, если они есть. При следующем запуске будет создана пустая база.
- Журнал действий записывается в `backend/audit.log`, если сервер запущен из папки `backend`.
- CSV формируется в UTF-8 с BOM для корректного открытия в Excel; ячейки с формулоподобным содержимым экранируются.

## 11. Сценарий демонстрации Hackathon

1. Запустите backend и Dashboard; откройте страницу и покажите пустое состояние и доступные статусы.
2. Подготовьте контролируемые тестовые HTTPS-сервисы: доверенный валидный сертификат, сертификат с коротким сроком, истёкший сертификат, self-signed, неправильную цепочку и сертификат с несовпадающим SAN.
3. Загрузите адреса тестовых сервисов списком; для URL можно задать нестандартный TLS-порт.
4. Укажите для одного сервиса владельца и критичность `CRITICAL`, а для другого оставьте владельца пустым.
5. Покажите статусы, детали сертификата, причины риска и рекомендации. Отфильтруйте `CRITICAL` и отсортируйте по дням до окончания.
6. Замените сертификат на одном тестовом сервисе и просканируйте его повторно. Покажите предупреждение ChangeGuard, старый/новый thumbprint, список отличий и изменение Risk Score.
7. Отметьте изменение проверенным, затем повторите сканирование без замены. Событие не должно появиться повторно.
8. Скачайте CSV. При настроенном Telegram покажите уведомления об изменении или достижении порога срока.
9. Перезапустите backend и покажите, что инвентарь и статус подтверждения изменения сохранились.

Используйте только адреса, которые разрешено проверять. Для демонстрации воспроизводимости предпочтительны локальные тестовые сервисы и тестовые сертификаты.

## 12. Устранение типовых проблем

| Симптом | Что проверить |
|---|---|
| Dashboard не загружает данные | Backend запущен на порту 8000; откройте `/health` и посмотрите окно backend |
| Сервис попал в список ошибок | DNS/IP разрешается с машины backend, порт доступен, целевой сервис говорит TLS на указанном порту |
| Цепочка отмечена ошибочной | Сертификат истёк, self-signed, CA не доверен ОС или сервер не отправляет необходимые промежуточные сертификаты |
| Имя не соответствует сертификату | Сверьте вводимый DNS/IP с SAN сертификата; для IP нужен соответствующий IP SAN |
| Telegram не прислал сообщение | Переменные заданы в терминале backend до старта, токен/чат верны, backend имеет доступ к Telegram API; повторное оповещение подавляется |
| Изменения схемы/данных не видны | Перезапустите backend; инвентарь хранится в указанном SQLite-файле |
| Порт 3000 или 8000 занят | Остановите другой процесс или освободите порт; frontend rewrite по умолчанию направлен на `localhost:8000` |

Ошибка сертификата не означает, что сканирование молча пропускает сервис: ошибки отдельных подключений возвращаются API и показываются в Dashboard.

## 13. Соответствие выбранной теме и границы MVP

Реализованы основные пункты темы 2: инвентаризация DNS/IP/TLS-сервисов, получение CN/SAN/Issuer/Thumbprint и срока действия, проверка доверия и имени, самоподписанных и слабых сертификатов, риск по критичности и владельцу, Dashboard, фильтры/сортировка, CSV и Telegram. Дополнительно ChangeGuard обнаруживает смену сертификата или его существенных проверяемых свойств между сканированиями и ведёт очередь изменений на ручную проверку. Сканер работает в режиме чтения: он получает публично предъявляемый сертификат и не пытается менять сервер.

MVP не выполняет автоматическое продление сертификатов, не хранит историю каждого сканирования, не проверяет закрытые внутренние реестры CA и не включает аутентификацию пользователей. Backend предназначен для локального стенда Hackathon; перед публикацией в общей сети необходимы аутентификация и разграничение доступа к запуску сканирования.
